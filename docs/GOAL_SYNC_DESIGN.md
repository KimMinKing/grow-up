# 목표·실천 기록 동기화 설계

기본 저장 위치는 기기입니다. Supabase 프로젝트에 `user_goal_snapshots` 마이그레이션을 적용했고, Android·웹 시험 빌드 `1.0.0+2018`에서 `GOAL_SYNC_ENABLED=true`로 계정 화면의 `지금 동기화` 버튼을 열었습니다. 사용자가 직접 누를 때만 목표와 기록을 전송하며 자동 동기화는 켜지지 않았습니다. 서버 업로드 중 로그인 계정이 바뀌면 동기화 기준본을 저장하지 않고 중단합니다.

## 저장 단위와 접근 권한

- 목표 하나의 기존 JSON을 스냅샷 하나로 저장합니다. 이 안에 실천 날짜·강도, 쉰 날, 로드맵 이정표, 선택한 계획, 보관 상태가 함께 들어 있습니다.
- 서버 키는 `(user_id, goal_id)`이며 로그인 사용자마다 같은 목표 ID를 별도로 가질 수 있습니다. 인증 사용자는 자기 행만 읽을 수 있고 테이블에 직접 쓸 수 없습니다.
- 쓰기는 `put_goal_snapshot(goal_id, snapshot, expected_revision)` RPC로만 합니다. 첫 업로드는 기대 버전 `0`, 이후에는 마지막으로 읽은 버전을 보냅니다. 서버 버전이 다르면 `null`을 반환하고 아무것도 덮어쓰지 않습니다.
- 서버 스냅샷은 최대 256 KiB이며, 앱에 이미 있는 목표 필드 형식을 유지합니다. 신수 이름과 테마는 이번 단계의 동기화 범위에 포함되지 않습니다.

## 앱의 수동 동기화

1. 첫 동기화에서 이 기기의 목표를 어느 계정에 연결할지 확인합니다. 로그인 사용자 ID별로 마지막 동기화 버전과 그때의 스냅샷을 로컬에 따로 보관합니다. 한번 동기화한 기기는 다른 계정으로 바로 동기화할 수 없게 막습니다.
2. 서버에서 자기 목표를 읽고 목표 ID별로 로컬·서버·체크포인트를 비교합니다. `decideGoalSync`가 첫 업로드, 첫 다운로드, 변경 없음, 충돌 중 하나를 결정합니다.
   서버에서 받은 모든 목표는 백업 파일과 같은 날짜·주간 기준·실천 자료 검사를 먼저 통과해야 합니다. 잘못된 목표가 하나라도 있으면 이번 동기화를 시작하지 않고 기존 로컬 기록을 유지합니다.
3. 한쪽만 바뀐 목표만 전송·수신합니다. 서버 쓰기는 기대 버전이 일치해야 성공합니다. 성공한 목표부터 체크포인트를 갱신하므로 일부만 전송된 뒤 실패해도 다음 동기화에서 이어갈 수 있습니다.
4. 두 기기에서 같은 목표를 고쳤다면 화면에서 날짜별 실천·쉼 기록과 이정표를 비교해 어느 쪽을 사용할지 선택합니다. 선택하지 않은 쪽은 **이 기기의 보관 목록**에 복사합니다. 보관본은 자동 전송되지 않습니다.

활성 목표는 앱에서 최대 5개입니다. 내려받기로 5개를 넘으면 충돌로 표시하며 기존 목표를 지우거나 자동 보관하지 않습니다. 이 경우 진행 중인 목표를 사용자가 보관한 뒤 다시 동기화해야 합니다. 현재 모델의 하루 기록은 날짜별 최종 상태만 저장하고 취소 이력·수정 시각은 없으므로 자동 병합하지 않습니다. 로그아웃해도 로컬 기록은 기기에 남습니다. 신수 이름과 테마는 동기화하지 않습니다.

검증은 PostgreSQL의 사용자별 읽기 권한·버전 거부 테스트와 가짜 서버를 이용한 앱의 업로드·다운로드·양쪽 변경·보관본 선택 테스트로 했습니다. 실제 Supabase 계정의 첫 동기화, 계정 간 접근 및 두 기기 동기화는 기기와 웹 호스팅이 준비되면 검증합니다.

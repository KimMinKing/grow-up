# 무료 뽑기 첫 버전

정식 파견 귀환 보상인 **뽑기 조각 3개**로 무료 뽑기 1회를 진행합니다. 유료 뽑기나 구매 재화는 없습니다. 서버 마이그레이션은 [`20261101010000_game_draws.sql`](../supabase/migrations/20261101010000_game_draws.sql)이며, 정식 파견 마이그레이션 뒤에 적용합니다.

## 확률과 보장

| 상황 | 결과 |
|---|---|
| 일반 뽑기 | 솔여우 50%, 파도수달 30%, 별까마귀 20% |
| 첫 뽑기 | 미발견 종이 있으면 그중 균등하게 한 종 |
| 5번째, 10번째, 15번째… 뽑기 | 미발견 종이 있으면 그중 균등하게 한 종 |
| 모든 종 발견 후 보장 차례 | 일반 확률 적용 |

첫 신수를 이미 보유한 계정은 첫 뽑기에서 다른 종을 얻습니다. 세 종을 모두 발견하기까지 최대 5회가 걸립니다. [`simulate_draws.py`](../scripts/simulate_draws.py)로 시작 종마다 10만 회를 실행했고 모두 5회 안에 세 종을 발견했습니다. 실제 PostgreSQL에서도 보장 규칙과 보상→뽑기 흐름을 검사했습니다. 시뮬레이션은 확률 분포 점검, SQL 테스트는 함수 동작 점검입니다.

## 재화와 보유 한도

- 서버가 조각 잔액과 보유 개체 수를 확인한 뒤, 같은 트랜잭션에서 조각 3개를 차감하고 신수 한 마리를 만듭니다.
- 20마리를 보유한 경우 뽑기를 거부하고 조각을 그대로 둡니다. 수령함과 개체 정리는 후속 기능으로 남깁니다.
- 같은 요청 ID를 재전송하면 기존 신수를 반환하고 조각을 다시 차감하지 않습니다. 앱은 응답이 끊겨도 같은 요청 ID를 기기에 보관합니다. 서버가 이미 조각을 차감해 잔액이 0개이거나 20칸이 찼어도 `이전 뽑기 결과 확인` 버튼으로 같은 요청을 재시도할 수 있습니다.
- 뽑은 신수는 서버 보유 목록에 저장되며 정식 파견 스쿼드의 빈 칸이나 기존 칸에 편성할 수 있습니다.

## 적용과 확인

1. [정식 파견 서버 설정](GAME_SERVER_SETUP.md)의 선행 마이그레이션을 적용합니다.
2. 뽑기 마이그레이션과 [`game_draws.sql`](../supabase/tests/game_draws.sql), [`game_reward_flow.sql`](../supabase/tests/game_reward_flow.sql)을 실제 PostgreSQL 시험 환경에서 실행합니다. 로컬 검증은 완료했고, 시험 파일은 마지막에 롤백합니다.
3. `GAME_REMOTE_ENABLED=true`, `GAME_DRAW_ENABLED=true`로 빌드해 로그인 후 파견 세 번을 마치고 조각 3개로 뽑습니다.
4. 첫 뽑기 미발견 보장, 서버 보유 목록·스쿼드 편성, 재실행 후 복구, 중복 요청에서 조각이 다시 줄지 않는지 확인합니다.

현재 Supabase 프로젝트에는 서버 테이블·함수가 배포되지 않았습니다. 이 화면은 두 빌드 옵션이 켜져도 서버 배포 전에는 사용할 수 없습니다.

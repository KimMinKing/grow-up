# 할 일·날짜별 메모 동기화

할 일과 메모는 기기에 저장되며 JSON 백업으로도 옮길 수 있습니다. 계정 화면의 **할 일·메모 동기화**를 직접 누르면 서버 기록과 비교합니다. 자동으로 서버에 올리거나 내려받지 않습니다. `DAILY_SYNC_ENABLED=true` 빌드에서 이 메뉴가 보입니다.

## 저장 단위

- 한 계정의 할 일·메모 목록 전체를 `user_daily_snapshots`의 한 행에 저장합니다. 키는 `user_id`, 내용은 `version: 1`, `tasks`, `notes`, `revision`입니다.
- 항목 삭제는 목록에서 사라진 상태로 기록합니다. 기기별 목록을 단순 합치면 삭제한 항목이 다시 나타날 수 있어, 전체 목록의 변경 버전을 비교합니다.
- 인증 사용자는 자기 행만 읽을 수 있습니다. 직접 쓰기는 막고 `put_daily_snapshot(snapshot, expected_revision)`으로만 씁니다. 서버 버전이 맞지 않으면 아무것도 덮어쓰지 않고 `null`을 반환합니다.
- 항목 형식과 날짜, ID 중복은 앱에서 검사합니다. 서버는 버전, 배열 크기, 전체 크기와 사용자 권한을 검사합니다. 최대 1000개씩, 전체 2 MiB입니다.

## 앱 동작 규칙

1. 로그인 사용자별로 마지막 동기화 버전과 그때의 목록을 기기에 보관합니다. 목표 동기화와 같은 계정 소유자 제한을 사용합니다.
2. 서버 자료를 읽으면 전체 목록을 검사한 뒤 로컬·서버·마지막 동기화본을 비교합니다. 서버 자료가 없는 첫 업로드와 마지막 동기화본을 기준으로 한쪽만 수정한 경우만 자동 진행합니다. 로컬 목록이 비어 있어도 이전에 항목을 모두 삭제했을 수 있으므로, 서버 자료가 있고 마지막 동기화본이 없으면 사용자 선택을 기다립니다.
3. 두 기기에서 각각 수정하거나 한쪽에서 삭제한 동안 다른 쪽이 수정했다면 충돌 화면에서 양쪽 목록을 비교해 선택하게 합니다. 선택하지 않은 목록은 이 기기의 JSON 보관본에 남기며 화면에서 전체 보기·복원할 수 있습니다. 보관본은 계정별 최근 10개까지 기기에 저장합니다. 사용자 선택 전에는 어느 쪽도 덮어쓰지 않습니다.
4. 충돌 없는 업로드도 서버의 기대 버전과 다르면 중단하고 새 자료를 다시 읽습니다. 앱이 오프라인이라면 로컬 변경을 유지하고 다음 수동 동기화에서 다시 비교합니다.

[SQL 마이그레이션](../supabase/migrations/20261101020000_daily_sync.sql), `DailySnapshot` 검증, 계정별 기준본, [동기화 서비스](../lib/state/daily_sync_service.dart), [충돌·보관본 화면](../lib/daily_sync_page.dart)을 연결했습니다. 보관본을 복원하면 기준본을 지워 다음 동기화에서 서버 기록과 다시 비교·선택합니다. 목표 동기화는 별도 `GOAL_SYNC_ENABLED`로 제어합니다.

## 추가 검증

로컬 PostgreSQL에서 숫자 대신 문자열인 버전과 배열이 아닌 목록을 거부하는지 확인했습니다. 같은 서버 버전으로 두 연결에서 동시에 수정할 때 한 요청만 성공하고 버전이 한 번만 증가하는 것도 확인했습니다. 앱 테스트에서는 충돌, 서버 버전 경쟁, 빈 기기의 서버 기록, 보관본 복원과 320dp·글자 200% 화면을 검사했습니다. 2026-11-07 플립4의 실제 로그인 계정에서 기기 할 일 2개를 처음 업로드하고, 다시 동기화했을 때 기기와 계정 기록이 같다는 판정을 확인했습니다. 앱을 강제 종료하고 다시 연 뒤에도 같은 판정이 유지됐습니다. 두 기기의 실제 충돌·보관본 복원 시험은 남았습니다.

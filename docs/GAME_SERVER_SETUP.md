# 정식 파견 서버 연결

게임 서버는 [정식 파견](../supabase/migrations/20261101000000_game_expeditions.sql), [첫 숲길 전투](../supabase/migrations/20261107000000_game_battle_attempts.sql), [할 일 전투권](../supabase/migrations/20261107010000_game_task_battle_passes.sql), [강가 전투 확장](../supabase/migrations/20261117000000_game_river_battles.sql), [재시도 동료 기록](../supabase/migrations/20261118000000_game_battle_retry_companion.sql)을 포함합니다. DB 마이그레이션 11개와 `verify-forest-battle` Edge Function을 `mpj` production 프로젝트에 적용했습니다. 플립4 로그인 계정에서 첫 신수 등록, 파견, 무료 뽑기, 숲길·강가 각 세 장소의 정식 전투와 앱 재실행 후 상태 복원을 확인했습니다.

## 규칙

- 계정마다 시작 신수 한 마리를 서버에 등록합니다. 서버의 시작 신수는 변경할 수 없습니다. 현재 기기의 훈련 신수 선택은 별도 로컬 자료입니다.
- 서버 신수는 최대 20마리, 스쿼드는 5칸입니다. 파견 중에는 서버 스쿼드를 바꿀 수 없습니다.
- 솔바람 숲 정식 파견은 서버 시계로 10분입니다. 한국 시간 자정 기준 하루 최대 3번 출발할 수 있습니다. 동시에 진행할 수 있는 파견은 하나입니다.
- `get_game_status`가 서버의 현재 시각과 오늘 출발 횟수를 반환합니다. 앱은 받은 시각에서 단조 증가 시계로 귀환 남은 시간을 계산하므로 기기 시계를 바꿔도 출발·귀환 버튼의 표시가 서버 판정과 어긋나지 않습니다.
- 귀환할 때 서버가 뽑기 조각 1개를 지급합니다. 같은 파견을 다시 청구하면 0개를 반환합니다. 조각 3개로 신수 한 마리를 무료 뽑습니다. 확률·보장·20마리 한도는 [무료 뽑기 설계](GAME_DRAW_DESIGN.md)에 있습니다.
- 클라이언트는 자신의 게임 자료만 읽을 수 있습니다. 파견·편성은 인증된 사용자의 RPC로 처리합니다. 정식 전투는 Edge Function이 서버 편성을 고정하고 전투 계산 뒤 서비스 역할로 결과를 확정합니다.
- 정식 전투는 한국 날짜로 하루 15회까지 도전할 수 있고 서버 전투권 1장을 사용합니다. 최근 30일의 동기화한 별도 할 일 완료마다 2장씩, 최대 30장까지 받습니다. 숲길 첫 승리에는 장소별 조각 1·1·2개와 배지를 지급하고, 편성 신수에는 승리 경험치를 지급합니다. 강가 첫 승리는 조각 없이 배지를 기록하며 물안개 여울에서 계정 자갈도롱뇽 한 마리를 지급합니다. [전투 보상 규칙](GAME_STAGE_REWARDS.md)

## 연결 순서

1. `supabase/migrations`의 마이그레이션 10개를 순서대로 적용했습니다. 네 번째는 [무료 뽑기](GAME_DRAW_DESIGN.md), 다섯 번째는 [할 일·메모 동기화 준비](DAILY_SYNC_DESIGN.md), 여섯 번째는 [첫 숲길 보상 원장](GAME_STAGE_REWARDS.md), 일곱 번째는 전투 증빙과 지급 조건, 여덟 번째는 전투 시도·서버 경험치·확정 RPC, 아홉 번째는 할 일 완료의 전투권 지급·소비 원장, 열 번째는 안개 강가 확장입니다. `verify-forest-battle` Edge Function도 재배포했습니다. 원격 마이그레이션 목록과 함수 `ACTIVE` 상태, 플립4의 강가 계정 전투 세 장소 첫 승리·보상·재실행 복원을 확인했습니다.
2. PostgreSQL에 접속할 수 있는 시험 환경에서 [`game_expeditions.sql`](../supabase/tests/game_expeditions.sql)을 실행합니다. 파일 전체가 `begin`/`rollback`으로 감싸져 시험 자료를 남기지 않습니다.
3. Galaxy Z Flip4에서는 인증번호 로그인과 업데이트 후 세션 복원을 확인했습니다. 현재 시험 설치본에는 `GAME_REMOTE_ENABLED=true`, `GAME_DRAW_ENABLED=true`, `GAME_STAGE_REWARDS_ENABLED=true`가 적용돼 정식 파견·뽑기·전투가 보입니다. 다른 빌드에서는 이 Dart define을 명시해야 합니다. [로그인 방법](AUTH_SETUP.md)
4. 2026-11-06 플립4에서 로그인한 계정의 카드를 열어 서버 동료 없음·뽑기 조각 0개·오늘 0/3회를 확인했습니다. 로컬 첫 동료 별까마귀를 서버에 등록하자 서버 보유 신수 1/20과 정식 파견 스쿼드 1번 칸에 반영됐습니다. 첫 출발 후 오늘 횟수 1/3과 귀환까지 10분이 표시됐고 앱을 강제 종료·재실행한 뒤에도 진행 상태와 남은 시간이 서버에서 복원됐습니다. 세 번 귀환해 조각이 0→1→2→3개로 늘었습니다. 2026-11-07 첫 무료 뽑기에서 미발견 솔여우를 얻어 조각 0개·서버 보유 2/20이 됐고 앱 강제 종료·재실행 후에도 유지됐습니다. 한국 자정 뒤 오늘 출발 횟수가 0/3으로 초기화된 것도 확인했습니다. 같은 귀환의 중복 수령 방지와 다른 계정 자료 격리는 로컬 PostgreSQL 테스트에서 확인했으며 실서비스 다중 계정·동시 요청 검증은 남았습니다.

앱은 `claim_game_starter`, `start_game_expedition`, `claim_game_expedition`, `set_game_squad_slot`으로 변경하고 `get_game_status`로 서버 시각·오늘 횟수를 읽습니다. 나머지 서버 자료는 테이블 읽기 정책으로 표시합니다. 서버 스쿼드와 로컬 훈련 스쿼드는 별도입니다.

로컬 보유 목록의 표시 순서와 관계없이 `starter-1` ID로 첫 신수를 찾아 서버 등록 후보를 정합니다. 정식 파견 카드에는 수동 새로고침이 있고 앱이 다시 활성화되면 서버 자료를 다시 읽습니다. 실제 계정의 출발·재실행 후 진행 상태 복원·귀환 조각 지급·첫 뽑기와 재실행 후 보유 상태를 확인했습니다.

## 로컬 PostgreSQL 검증

Flutter 화면 테스트는 가짜 서버로 첫 신수 등록→3회 파견·귀환→조각 3개→무료 뽑기→새 신수 표시를 확인했습니다. 로그아웃 상태의 정식 파견 카드에는 계정 로그인 버튼이 있으며 300dp 에뮬레이터에서 이동과 표시를 확인했습니다. 실제 Supabase 계정에서도 첫 신수 등록·파견 3회 귀환·조각 3개 첫 뽑기·상태 복원까지 확인했습니다.

마이그레이션 10개와 SQL 테스트를 **실제 PostgreSQL 16**에서 실행했습니다. Ubuntu/WSL에 PostgreSQL을 설치해 서버를 시작한 뒤 다음처럼 재현할 수 있습니다. 스크립트는 일회용 DB를 만들고 테스트가 끝나면 삭제합니다. `local_supabase_bootstrap.sql`은 로컬 테스트에 필요한 최소 Auth 역할·함수만 제공하며 실제 Supabase 프로젝트에 적용하지 않습니다.

```bash
sudo pg_ctlcluster 16 main start
sudo -u postgres bash scripts/test_supabase_local.sh
```

`game_expeditions.sql`은 계정 격리, 중복 출발·귀환, 한국 날짜의 일일 횟수 경계를 검사합니다. `game_draws.sql`은 보장 뽑기, 중복 요청, 20마리 한도 등을 검사합니다. `game_reward_flow.sql`은 세 번의 파견 보상으로 조각 3개를 모아 첫 뽑기를 하고 같은 요청을 재시도하는 전체 경로를 검사합니다. `game_stage_first_clears.sql`은 인증된 앱의 증빙 생성·지급 권한 차단, 미검증 전투 지급 거절, 선행 장소, 중복 지급, 계정 격리를 검사합니다. `game_battle_attempts.sql`과 `game_river_battles.sql`은 숲길·강가의 동료 지급을 시도에 기록해 재시도에서도 찾을 수 있는지, 20마리 한도에서는 기록하지 않는지 검사합니다. AI 사용량과 목표 동기화 SQL 테스트도 같은 실행에 포함됩니다.

마지막으로 `game_concurrency.sh`가 두 DB 연결에서 같은 계정의 출발·귀환 보상·뽑기·첫 승리 지급·전투 완료 요청을 동시에 보내 각 상태 변화가 한 번만 일어나는지 확인합니다.

로컬 검증은 실제 Supabase 프로젝트의 Auth·API와 앱 실동작 검증을 대신하지 않습니다. 원격 배포 후 앱 계정의 증빙 쓰기·지급 함수 실행 및 서버 역할의 첫 승리 원장 직접 쓰기가 차단된 것을 읽기 전용으로 확인했습니다. 첫 숲길 전투는 실제 플립4 계정에서 세 장소의 첫 승리, 반복 성장, 보스 재도전과 재실행 후 상태 복원까지 확인했습니다. 다른 계정과 두 기기를 이용한 실서비스 동시성 검증은 남았습니다.
